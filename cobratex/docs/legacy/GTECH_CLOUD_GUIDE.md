# دليل شامل: النشر السحابي، بناء/تعديل بلوجن تصنيع جديد، وتعدد العملاء (G-Tech ERP)

هذا الدليل يغطي ثلاثة أشياء بالتفصيل:
1. **ربط البرنامج بالسحابة** خطوة بخطوة (مجانًا بالكامل).
2. **بناء/تعديل نشاط تصنيع** (لا يحتاج كودًا في أغلب الحالات)، وفرق ذلك عن "الإضافات" الحقيقية في هذا المشروع، وكيفية نشر أي تعديل كود فعليًا على السحابة.
3. **تشغيل المشروع لأكثر من عميل** على نفس النشر المجاني، مع الفصل الفعلي بين بياناتهم.

كل خطوة هنا تحققتُ منها فعليًا (بناء نظيف، migrations، 328 اختبارًا تلقائيًا) قبل كتابتها هنا — لا خطوة نظرية غير مجرَّبة.

## القسم 1: ربط البرنامج بالسحابة (مجانًا بالكامل)

### 1.1 الصورة العامة

المشروع 3 قطع منفصلة، كل واحدة على خدمة مجانية مختلفة:

| القطعة | الخدمة المقترحة (مجانية) | لماذا هذه بالذات |
|---|---|---|
| قاعدة البيانات (PostgreSQL) | **Neon** (أو Supabase) | مجانية **دائمًا** (لا فترة تجريبية تنتهي)، تدعم PostgreSQL 16 كاملًا |
| الباك إند (Node.js API) | **Render** (Free Web Service) | يقرأ `backend/render.yaml` تلقائيًا، يبني الصورة من `backend/Dockerfile` |
| الواجهة (React SPA) | **Vercel** (أو Netlify) | يقرأ `frontend/vercel.json` (أو `netlify.toml`) تلقائيًا |

الثلاثة ملفات (`render.yaml`, `Dockerfile`, `vercel.json`/`netlify.toml`) **موجودة بالفعل في المستودع** — لا تحتاج كتابتها، فقط ربط الحسابات.

### 1.2 خطوة 1: قاعدة البيانات على Neon

1. اذهب إلى [neon.tech](https://neon.tech) → أنشئ حسابًا مجانيًا (بريد إلكتروني أو GitHub).
2. **Create a project** → اختر أي اسم ومنطقة جغرافية قريبة منك.
3. بعد الإنشاء، Neon يعرض **Connection string** جاهزًا — انسخه. شكله:
   ```
   postgresql://USER:PASSWORD@ep-xxxxx.region.aws.neon.tech/neondb?sslmode=require
   ```
4. احتفظ به جانبًا — ستحتاجه في الخطوة التالية بالضبط كما هو (لا تُعدِّل فيه شيئًا).

**ملاحظة**: الخطة المجانية في Neon محدودة بحجم تخزين (عادة حوالي 0.5GB) وساعات حوسبة شهرية — كافية جدًا لتجربة حقيقية أو عدد قليل من العملاء الصغار (راجع القسم 3.4 لتفاصيل الحدود).

### 1.3 خطوة 2: الباك إند على Render

1. اذهب إلى [render.com](https://render.com) → أنشئ حسابًا (يُفضَّل الربط المباشر بحساب GitHub الخاص بك حتى يرى Render المستودع).
2. من لوحة Render: **New** → **Blueprint**.
3. اختر المستودع (Repository) الذي يحتوي هذا المشروع. Render يكتشف `backend/render.yaml` تلقائيًا ويعرض الخدمة المُعرَّفة فيه (`gtech-erp-backend`).
4. عند الضغط على **Apply**، سيطلب منك Render قيم المتغيرات السرّية (المُعلَّمة `sync: false` في الملف):
   - **`DATABASE_URL`**: الصق رابط الاتصال من Neon (خطوة 1.2).
   - **`BOOTSTRAP_SECRET`**: Render يولِّده تلقائيًا (`generateValue: true`) — **انسخه واحفظه في مكان آمن** (مدير كلمات مرور)، ستحتاجه لاحقًا لإنشاء أي شركة/عميل جديد (راجع 1.5 والقسم 3).
   - **`JWT_ACCESS_SECRET`** و**`JWT_REFRESH_SECRET`**: يولِّدهما Render تلقائيًا، لا تفعل شيئًا.
   - **`VAPID_PUBLIC_KEY`**/`VAPID_PRIVATE_KEY`/`VAPID_SUBJECT`: اختيارية (إشعارات فورية) — اتركها فارغة الآن، يمكن ضبطها لاحقًا من **Environment** في لوحة الخدمة.
   - **`UPDATE_FEED_URL`**: اختياري، اتركه فارغًا.
5. اضغط **Deploy**. Render يبني صورة Docker وينشرها (أول بناء يأخذ 3-5 دقائق).
6. عند النشر، أمر تشغيل الحاوية (في `Dockerfile`) يُطبِّق **كل الـ migrations تلقائيًا** قبل بدء الخادم — لا حاجة لأي أمر يدوي.
7. بعد نجاح النشر، Render يعطيك رابطًا مثل:
   ```
   https://gtech-erp-backend.onrender.com
   ```
   احتفظ به — عنوان الـ API الفعلي هو هذا الرابط + `/api`.

**تحقَّق من نجاح هذه الخطوة** قبل المتابعة:
```bash
curl https://gtech-erp-backend.onrender.com/api/system/version
```
يجب أن يُعيد نسخة البرنامج (JSON). لو أعاد خطأ اتصال، راجع تبويب **Logs** في Render أولًا (غالبًا `DATABASE_URL` خاطئ أو قاعدة Neon لم تُفعَّل بعد).

### 1.4 خطوة 3: الواجهة على Vercel

1. اذهب إلى [vercel.com](https://vercel.com) → أنشئ حسابًا (يُفضَّل GitHub).
2. **Add New** → **Project** → اختر نفس المستودع.
3. في إعدادات الاستيراد: **Root Directory** = `frontend` (مهم جدًا — المشروع يحتوي مجلدين، Vercel يحتاج يعرف أيهما).
4. **Environment Variables** → أضف:
   ```
   VITE_API_BASE_URL = https://gtech-erp-backend.onrender.com/api
   ```
   (استبدل الرابط برابط الباك إند الفعلي من الخطوة السابقة، بلا شرطة مائلة زائدة في النهاية).
5. **Deploy**. Vercel يقرأ `frontend/vercel.json` تلقائيًا (يضبط توجيه SPA بنفسه — لا تحتاج تعديل شيء).
6. بعد النشر، يعطيك رابطًا مثل `https://your-project.vercel.app` — هذا رابط التطبيق الذي يستخدمه الموظفون/العملاء.

### 1.5 خطوة 4: إنشاء أول شركة (Tenant)

لا توجد شاشة "تسجيل" في الواجهة بعد — إنشاء أول شركة يتم عبر استدعاء مباشر لمسار `/bootstrap` (مرة واحدة فقط لكل شركة):

```bash
curl -X POST https://gtech-erp-backend.onrender.com/api/bootstrap \
  -H "Content-Type: application/json" \
  -H "x-bootstrap-secret: <القيمة التي حفظتها من Render في 1.3>" \
  -d '{
    "tenantName": "اسم الشركة",
    "companyLegalName": "الاسم القانوني للشركة",
    "ownerEmail": "admin@example.com",
    "ownerPassword": "كلمة مرور قوية"
  }'
```

الاستجابة (JSON) تتضمن `tenantId` — **احتفظ به**، فهو مطلوب عند تسجيل الدخول من الواجهة (تصميم متعمَّد لدعم تعدد الشركات، راجع القسم 3).

> **ترويسة `x-bootstrap-secret` إلزامية الآن**: أضفتها في هذه المراجعة لأن هذا المسار ينشئ حسابات مالك كاملة — بلا حماية، أي زائر على الإنترنت يستطيع إنشاء شركات بلا حد على قاعدتك المشتركة. القيمة هي `BOOTSTRAP_SECRET` التي ولَّدها Render في الخطوة 1.3. بلا ضبط هذا المتغير أصلًا (كما في التطوير المحلي بلا `.env`)، يبقى المسار مفتوحًا كسابقًا — **لا تنشر بدونه**.

افتح رابط Vercel من الخطوة السابقة، سجّل الدخول بـ`tenantId` + البريد/كلمة المرور اللذين استخدمتهما.

### 1.6 قائمة فحص نهائية

- [ ] `curl .../api/system/version` يُعيد استجابة ناجحة
- [ ] تسجيل الدخول من الواجهة ينجح ويعرض لوحة الرئيسية
- [ ] إنشاء عميل تجريبي وفاتورة بيع مسودة ينجح
- [ ] ترحيل الفاتورة ينجح (يعني القيود المحاسبية تعمل فعليًا)

### 1.7 قيود واقعية على الخطة المجانية

- **Render Free ينام بعد 15 دقيقة بلا طلبات**، ثم يستيقظ تلقائيًا عند أول طلب (تأخير ~30 ثانية على أول طلب فقط). مقبول لمرحلة تجريبية أو استخدام داخلي محدود، غير مناسب لعملاء يتوقعون استجابة فورية دومًا (الحل المدفوع: ترقية الخطة، أو خدمة "keep-alive" خارجية تستدعي `/api/system/version` كل بضع دقائق — حل ملتوٍ، ذكرته للأمانة لا كتوصية).
- **Neon Free**: تخزين وساعات حوسبة محدودة شهريًا — راقب استهلاكك من لوحة Neon نفسها.
- لا نطاق مخصَّص (custom domain) تلقائيًا — كل من Render وVercel يدعمانه مجانًا (شهادة SSL تلقائية) من إعدادات الخدمة إن أردت رابطًا باسمك بدل `onrender.com`/`vercel.app`.

## القسم 2: بناء/تعديل نشاط تصنيع، والفرق بين ذلك وبين "الإضافات" الحقيقية

### 2.1 نوعان مختلفان تمامًا من "التوسعة" في هذا المشروع — مهم جدًا أن تفرّق بينهما

| | **نشاط تصنيع جديد (BOM)** | **إضافة/بلوجن خارجي (plugins/)** |
|---|---|---|
| مثال | "غزل قطن"، "نسيج قماش"، "تجميع أثاث"، أي صناعة | صفحة/تكامل خارجي مستقل تمامًا عن المحاسبة والمخزون |
| يحتاج كودًا؟ | **لا** — عبر واجهة التطبيق فقط | نعم — ملف JS جديد |
| مثال جاهز بالمشروع | — | `backend/plugins/hello-activity/` |
| آمن ماليًا؟ | نعم — نفس محرك القيود والمخزون المُختبَر | لا ضمانة نوعية (TypeScript) ولا اختبارات تلقائية |

**القاعدة العملية**: أي نشاط تصنيع جديد — مهما اختلفت الصناعة — **لا يحتاج أي تعديل كود إطلاقًا**. هذا هو بالضبط سبب بناء وحدة التصنيع بلا أي افتراض عن صناعة معيّنة منذ البداية.

### 2.2 الحالة الأولى (الأشيع): نشاط تصنيع جديد بلا أي كود

من داخل التطبيق نفسه:

1. **الأنشطة** (`/manufacturing` → قسم الأنشطة): أنشئ نشاطًا جديدًا باسمه (مثال: "غزل"، "نسيج"، "تجميع"). هذا تصنيف اختياري فقط، لا يغيّر أي سلوك.
2. **قوائم المواد** (`/manufacturing/boms/new`): أنشئ وصفة جديدة —
   - الصنف الناتج (أي صنف، بأي اسم/نوع تريده).
   - المكوّنات: أي أصناف أخرى + الكمية اللازمة لكل منها + **نسبة الهالك** إن وُجدت (مثال: 5% يعني تحتاج 5% مادة خام إضافية عن الكمية النظرية لتعويض الفاقد أثناء التشغيل).
   - مراحل التصنيع (اختياري): اسم كل مرحلة (غزل، نسيج، تشطيب...) + نوعها (عمالة/مصاريف تشغيل) + تكلفتها.
3. **أمر تصنيع** (`/manufacturing/orders/new`): اختر الوصفة + الكمية المطلوب إنتاجها → "تنفيذ الأمر". النظام يحسب الاستهلاك الفعلي والتكلفة وينشئ القيد المحاسبي تلقائيًا.
4. **تسلسل مراحل بدون أي إعداد إضافي**: لو نشاطك يمر بمرحلتين منفصلتين (مثلًا خام → خيط عبر الغزل، ثم خيط → قماش عبر النسيج)، فقط اجعل الوصفة الأولى تُنتج "خيط"، والوصفة الثانية تستهلك "خيط" (نفس الصنف) وتُنتج "قماش". نفِّذ أمر الغزل أولًا، ثم أمر النسيج — مُختبَر ويعمل تمامًا هكذا.

هذا يغطي عمليًا أي نشاط تصنيعي متعدد المراحل، بلا أي عمل هندسي.

### 2.3 الحالة الثانية: تعديل منطق وحدة التصنيع نفسها (يحتاج كودًا فعليًا)

إن أردت تغييرًا في **طريقة عمل** الوحدة نفسها (مثال: معادلة تكلفة مختلفة، حقل جديد، قاعدة تحقق مختلفة) — هذا تعديل كود TypeScript عادي، لا "بلوجن":

**أين الكود**:
- الباك إند: `backend/src/modules/manufacturing/` (كل شيء: القاعدة، الخدمة، المسارات، معزولة بالكامل هنا).
- الواجهة: `frontend/src/features/manufacturing/`.
- الاختبارات: `backend/tests/manufacturing.test.ts` (20 اختبارًا حاليًا تغطي كل سيناريو — أي تعديل، شغِّلها أولًا للتأكد أنك لم تكسر شيئًا).

**خطوات التعديل والنشر**:
1. عدِّل الكود محليًا.
2. شغِّل الاختبارات محليًا: `cd backend && npm test` (يحتاج PostgreSQL محليًا — راجع قسم "تشغيل الباك إند محليًا" في `README.md`).
3. Commit + Push لفرع (branch) أو مباشرة لـ`main` حسب سير عملك.
4. **GitHub Actions CI** (`.github/workflows/ci.yml`) يشغِّل تلقائيًا: فحص الأنواع + كل الـ migrations من الصفر + كل الاختبارات (باك إند)، وفحص الأنواع + lint + البناء (واجهة). راقب تبويب **Actions** في GitHub — لو فشل أي شيء، **لا تنشر** حتى يُصلَح.
5. **النشر الفعلي**:
   - **Render**: لو ربطت الخدمة بفرع `main` في GitHub (الخيار الافتراضي عند إنشاء Blueprint)، كل push لهذا الفرع يُطلق نشرًا تلقائيًا (يبني صورة Docker جديدة من الصفر، يُطبِّق أي migration جديدة تلقائيًا، ثم يبدِّل الخدمة القديمة بالجديدة بلا انقطاع محسوس). يمكنك أيضًا الضغط يدويًا على **Manual Deploy** من لوحة Render.
   - **Vercel**: نفس الفكرة تمامًا — push يُطلق بناءً ونشرًا تلقائيًا للواجهة.
6. تحقَّق بعد النشر بنفس قائمة الفحص في 1.6.

**نقطة حاسمة**: لو أضفت migration جديدة (ملف SQL في `backend/src/db/migrations/`)، فهي تُطبَّق تلقائيًا عند كل نشر (أمر `Dockerfile` يُشغِّلها قبل بدء الخادم) — **لا تحتاج تدخلًا يدويًا على قاعدة الإنتاج**، لكن تأكَّد أنها مُختبَرة محليًا على نسخة من البيانات أولًا لو كانت تُعدِّل جداول فيها بيانات حقيقية بالفعل.

### 2.4 الحالة الثالثة: إضافة خارجية حقيقية (بنمط `plugins/`) — مثال كامل

هذا فقط لو أردت شيئًا **مستقلًا تمامًا** عن المحاسبة/المخزون (تكامل مع خدمة خارجية، صفحة معلومات، أداة مساعدة). اتبع نمط `backend/plugins/hello-activity/` بالضبط:

```
backend/plugins/my-plugin/
  plugin.json          ← بيانات وصفية
  index.js              ← مسارات API (CommonJS عادي، بلا TypeScript)
  frontend/entry.js      ← اختياري: عنصر واجهة (Web Component خام)
```

**`plugin.json`**:
```json
{
  "name": "my-plugin",
  "version": "1.0.0",
  "description": "وصف مختصر",
  "enabled": true,
  "frontendEntry": "frontend/entry.js",
  "customElementTag": "my-plugin-widget",
  "navLabel": "اسم الرابط في القائمة الجانبية"
}
```

**`index.js`** (مثال أدنى):
```js
module.exports = {
  registerRoutes(router, sdk) {
    // sdk.pool: اتصال قاعدة البيانات المشترك — يمكنك إنشاء جداولك الخاصة (بادئة باسم إضافتك)
    router.get('/plugins/my-plugin/hello', (req, res) => {
      // req.ctx متاح تلقائيًا (هوية المستخدم/الشركة/الفرع) — نفس عزل الشركة على كل شيء آخر
      res.json({ message: 'مرحبًا', company: req.ctx.companyId });
    });
  },
};
```

**`frontend/entry.js`**: انسخ `backend/plugins/hello-activity/frontend/entry.js` كنقطة بداية وعدِّل المحتوى — القاعدة الوحيدة: Web Component خام (`customElements.define`)، بلا React، بلا أي استيراد من حزم التطبيق.

**محليًا**: أسقط المجلد، أعِد تشغيل `npm run dev` في الباك إند (أو حتى بلا إعادة تشغيل لو تستخدم `ts-node-dev` الذي يراقب التغييرات) — تظهر فورًا، **بلا** `npm run build`.

**⚠️ على Render تحديدًا — فرق مهم عن "محليًا"**: الملاحظة في `README.md` الحالي ("إسقاط مجلد وإعادة تشغيل العملية فقط، بلا إعادة بناء") **صحيحة محليًا فقط**. على Render، حسب `Dockerfile`، مجلد `plugins/` **يُنسَخ داخل صورة Docker وقت البناء**:
```dockerfile
COPY --from=build /app/plugins ./plugins
```
Render لا يوفِّر قرصًا دائمًا (Persistent Disk) في الخطة المجانية، فأي تعديل على ملفات الإضافة يحتاج **نفس دورة commit → push → إعادة بناء ونشر** الموضَّحة في 2.3 — وليس مجرد "استبدال ملف على الخادم". لو أردت فعلًا استبدال ملفات إضافة **بلا** إعادة بناء الصورة كاملة على أي بيئة سحابية، الخيار الوحيد عمليًا هو استضافة تدعم أقراصًا دائمة مجانية جزئيًا (مثل Fly.io ضمن حدود معيّنة) وربط مجلد `plugins/` بها كـ Volume — إعداد إضافي خارج نطاق هذا الدليل، اذكره فقط لو احتجته فعلًا.

### 2.5 إلغاء وحدة التصنيع بالكامل لشركة معيّنة (بلا حذف كود)

من صفحة `/manufacturing` نفسها (تبقى دائمًا في القائمة الجانبية) → مفتاح التشغيل في الأعلى. الإيقاف يجعل كل طلبات الوحدة تُرفَض وكأنها غير موجودة، بلا أي حذف بيانات — إعادة التفعيل تُعيد كل شيء كما كان فورًا.

**للحذف الفعلي من الكود** (نادرًا ما تحتاجه، فقط لو قررتم نهائيًا عدم استخدام التصنيع إطلاقًا في أي فرع مستقبلي من المشروع):
- احذف `backend/src/modules/manufacturing/` بالكامل.
- احذف `frontend/src/features/manufacturing/` بالكامل.
- احذف سطر `app.use('/api', authMiddleware, manufacturingRouter);` من `backend/src/app.ts`.

## القسم 3: تشغيل المشروع لأكثر من عميل على نفس النشر المجاني (فصل البيانات)

### 3.1 الخبر الجيد: هذا مبني في قاعدة البيانات نفسها من البداية

هرم البيانات: **Tenant (مستأجر)** ← **Company (شركة)** ← **Branch (فرع)** ← **Warehouse (مخزن)**. كل جدول في قاعدة البيانات تقريبًا (عملاء، موردون، فواتير، مخزون، خزينة، تصنيع...) له عمود `company_id`، وكل استعلام في كل خدمة خلفية **مُقيَّد به تلقائيًا** من التوكن (JWT) الذي يحمله المستخدم بعد تسجيل الدخول — لا استثناء واحد.

هذا ليس ادّعاءً نظريًا: **عشرات اختبارات "عزل الشركات" موجودة فعليًا** في كل ملف اختبار تقريبًا عبر المشروع (مثال: `manufacturing.test.ts`، `bankReconciliation.test.ts`، `stocktake.test.ts`، `attachments.test.ts`، وغيرها) — كل واحد ينشئ شركتين منفصلتين، ويتحقق فعليًا أن بيانات إحداهما غير مرئية للأخرى بأي شكل.

**خلاصة عملية**: نعم، يمكنك تشغيل نفس النشر (نفس خادم Render، نفس قاعدة Neon) لعدد عملاء، وكل عميل يرى بياناته فقط، بلا أي تعديل كود إضافي.

### 3.2 كيف تضيف عميلًا جديدًا

كرِّر خطوة 1.5 بالضبط — بيانات مختلفة فقط:

```bash
curl -X POST https://gtech-erp-backend.onrender.com/api/bootstrap \
  -H "Content-Type: application/json" \
  -H "x-bootstrap-secret: <القيمة نفسها من Render>" \
  -d '{
    "tenantName": "اسم العميل الثاني",
    "companyLegalName": "الاسم القانوني للعميل الثاني",
    "ownerEmail": "owner@client2.com",
    "ownerPassword": "كلمة مرور قوية مختلفة"
  }'
```

احفظ `tenantId` الذي يعود في الاستجابة، وأعطِه + بريد/كلمة مرور المالك للعميل. هذا كل ما يحتاجه — نفس رابط الواجهة (Vercel) بالضبط لكل العملاء، يُفرَّق بينهم بـ`tenantId` وقت تسجيل الدخول فقط.

### 3.3 ماذا يرى كل عميل فعليًا

- تسجيل الدخول يتطلب `tenantId` + البريد + كلمة المرور معًا — لا طريقة لتخمين أو استنتاج شركة أخرى.
- بعد الدخول، كل شاشة (العملاء، الفواتير، المخزون، التصنيع، التقارير...) تعرض بيانات شركته فقط.
- لا قائمة "بديلة" أو رابط خفي يكشف وجود عملاء آخرين على نفس الخادم.

### 3.4 حدود هذا النموذج على الخطة المجانية تحديدًا (بصراحة كاملة)

- **خادم واحد مشترك (Render Free)**: كل العملاء يتشاركون نفس المعالج/الذاكرة المحدودة لخطة Render المجانية. لعدد قليل من العملاء الصغار (بضع شركات، استخدام غير مكثَّف)، هذا مقبول تمامًا. لعملاء كثر أو استخدام مكثَّف متزامن، الأداء سيتأثر للجميع معًا — عندها الترقية لخطة مدفوعة (أو فصل كل عميل على خدمة Render منفصلة) هي الحل، لا تعديل كود.
- **قاعدة بيانات واحدة مشتركة (Neon Free)**: نفس الفكرة — حدود التخزين وساعات الحوسبة الشهرية مشتركة بين كل العملاء معًا، لا لكل عميل على حدة.
- **لا لوحة إدارة** حاليًا لعرض/تعطيل/حذف مستأجر معيّن من الواجهة — فقط عبر اتصال مباشر بقاعدة البيانات (`psql` أو أداة مثل Neon's SQL editor) إن احتجت ذلك. هذا حد صريح في النسخة الحالية، وليس خطأ سهوًا — يمكن بناء لوحة كهذه لاحقًا كمهمة منفصلة لو احتجتها فعليًا.

### 3.5 بديل أقوى عزلًا (لو احتجته لاحقًا: عزل فعلي على مستوى البنية التحتية لا الصفوف فقط)

النموذج أعلاه (Row-Level Isolation في قاعدة واحدة) هو الأنسب لخطة مجانية — يشارك التكلفة بين كل العملاء. لو عميل معيّن يحتاج ضمان عزل أقوى (مثال: متطلب امتثال يفرض قاعدة بيانات منفصلة فعليًا)، البديل هو **نشر منفصل بالكامل** لذلك العميل: كرِّر القسم 1 كاملًا (مشروع Neon جديد + خدمة Render جديدة + مشروع Vercel جديد) — كل الملفات (`render.yaml`, `Dockerfile`, إلخ) نفسها تُستخدَم بلا تعديل، فقط ربط جديد بحسابات مختلفة. كل الثلاث خدمات (Neon/Render/Vercel) تسمح بعدة مشاريع مجانية منفصلة تحت نفس الحساب، فهذا ممكن فعليًا على الخطط المجانية أيضًا لعدد محدود من العملاء، لكنه يفقد ميزة مشاركة التكلفة/الصيانة لنموذج القاعدة المشتركة.
