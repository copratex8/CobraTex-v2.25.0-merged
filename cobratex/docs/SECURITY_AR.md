# الأمان ونموذج التسليم للعملاء

## 1) ماذا يستلم العميل وماذا يبقى عندك
| | العميل يحصل على | يبقى عندك فقط |
|---|---|---|
| **رابط (PWA)** | رابط الموقع، يثبّته كتطبيق على الجوال/الويندوز من المتصفح | كود الباك إند، دوال/جداول قاعدة البيانات، مفتاح `service_role`، لوحة المطور، أسرار JWT، مستودع GitHub |
| **ملف .exe** | مثبّت صغير (`desktop-shell`) لا يحتوي إلا **عنوان رابطك** ونافذة مقفلة | كل ما سبق. الـ exe لا يحتوي كودًا ولا قاعدة بيانات ولا خادمًا |

التحديثات تصل العميل تلقائيًا (الموقع يتحدّث على الخادم؛ والـ exe يفتح الرابط نفسه) دون إعادة تسليم أي ملف.
**بناء الـ exe:** GitHub → Actions → «Build Windows installer» → Run workflow → أدخل رابط العميل واسمه. يمكنك بناء مثبّت مستقل لكل عميل. بدون شهادة توقيع (Code Signing) سيعرض ويندوز تحذير SmartScreen عند التثبيت؛ إن امتلكت شهادة أضفها كسرّين `WIN_CSC_LINK` و`WIN_CSC_KEY_PASSWORD`.

## 2) حدود الحماية (بصراحة)
- **ملفات JavaScript للواجهة تصل إلى متصفح العميل دائمًا** (هذه طبيعة الويب). ما يحميك: لا يوجد أي منطق حسّاس أو سر فيها؛ كل شيء مهم يعمل على الخادم أو داخل القاعدة خلف RLS. وأوقفنا الـ source maps وأزلنا التعليقات فلا تصل ملفات TypeScript الأصلية.
- مفتاح `anon` ظاهر للعميل **بالتصميم** — حمايته هي سياسات RLS التي يفحصها الـ CI.
- مفتاح `service_role` يعادل صلاحية مالك القاعدة: لا يوضع إلا في سكربتات تعمل على جهازك. فاحص الأسرار يمنع رفعه للمستودع، واختبار البناء يتأكد أنه غير موجود في الـ bundle.
- تحكمك في العملاء: لوحة المطور تُوقف عميلًا محددًا أو المنصة كلها (تقطع الدخول والقراءة والكتابة والـ Realtime فورًا). هذا يحميك من عدم السداد.

## 3) ما أُغلق في الكود
| الثغرة | الإصلاح |
|---|---|
| دوال `public` في القاعدة (مثل `seed_textile_defaults`) كانت قابلة للاستدعاء من أي مستخدم/زائر عبر API لشركة أخرى | `…07_harden_functions.sql` يسحب التنفيذ منها؛ ويفحصه اختبار RLS واختبار الدخان |
| `/bootstrap` مفتوح للعالم إن لم يُضبط `BOOTSTRAP_SECRET` (إنشاء مستأجرين بلا حد) | في الإنتاج بلا السر يصبح المسار 404؛ ومقارنة السر بزمن ثابت |
| تشغيل الإنتاج بأسرار JWT افتراضية/ضعيفة | الخادم يرفض الإقلاع (أقل من 32 حرفًا أو `change-me`) |
| حدّ محاولات الدخول يحسب IP بروكسي Vercel لا IP المهاجم | `trust proxy` على Vercel |
| مسار دخول ثانٍ (`/auth/login`) بحدّ في الذاكرة لا يصمد على Serverless | `DISABLE_LEGACY_LOGIN=true` يغلقه؛ الدخول عبر Supabase Auth فقط |
| تسجيل مستخدمين من الإنترنت عبر مفتاح anon | خطوة إلزامية في لوحة Supabase + فحص آلي في اختبار الدخان |
| تسريب `password_hash`/`mfa_secret` و`audit_logs` و`backup_settings` عبر Data API | أعمدة/جداول محجوبة + اختبارات RLS |
| كتابة مباشرة من المتصفح للجداول | سحب INSERT/UPDATE/DELETE عن `authenticated` |
| CORS مفتوح لأي موقع | `CORS_ORIGINS` يقيّده (يشمل لوحة المطور) |
| ترويسات الأمان ناقصة | `X-Frame-Options`, `HSTS`, `Permissions-Policy`, `nosniff`؛ وCSP اختياري (`VITE_CSP=on`) |
| تسريب أسرار/مفاتيح في المستودع | `tools/secret-scan.mjs` في كل push وأسبوعيًا (جُرّب بتسريبات مزروعة فكشفها) |
| مكتبات بثغرات معروفة | `npm audit` أسبوعيًا + Dependabot |
| الـ exe | نافذة معزولة (sandbox)، بلا Node، التنقل مقفل على نطاقك، كل الأذونات مرفوضة، https إلزامي |

### إضافات هذه الدفعة
| الثغرة المحتملة | الإصلاح |
|---|---|
| لوحة المطور = مفتاحك الرئيسي بعامل واحد | 2FA (TOTP) لا يُقبل رمزه مرتين، رسالة فشل واحدة (لا تكشف أي عامل أخطأ)، تقييد IP اختياري، جلسة 4 ساعات، تسجيل كل محاولة دخول، وترويسة CSP للوحة |
| لا واجهة/واجهة API لإدارة المستخدمين (كان الإنشاء برمجيًا فقط) | وحدة مستخدمين وأدوار كاملة + منع تصعيد الصلاحيات + حماية آخر مالك + إنهاء الجلسات عند تغيير كلمة المرور/التعطيل |
| عميل متأخر عن السداد يبقى يعمل | إيقاف/قراءة فقط تلقائيًا بعد انتهاء الترخيص + فترة السماح على مستوى الخادم **و**RLS |
| أجهزة قديمة بإصدار به ثغرة | «أدنى إصدار» إجباري يمنع العمل حتى التحديث |
| عملاء متعددون بمفتاح واحد | نشر مستقل لكل عميل بأسرار فريدة (JWT/Developer/Bootstrap/2FA/Cron) |

## 4) إعدادات لوحة Supabase (يدوية — لا يمكن للكود فعلها)
- [ ] **Authentication → Sign In / Providers → عطّل «Allow new users to sign up»**.
- [ ] Authentication → Hooks: فعّل `custom_access_token_hook`.
- [ ] Authentication → Attack Protection: فعّل **CAPTCHA** (Turnstile/hCaptcha) إن رغبت، وراجع حدود المعدّل.
- [ ] Authentication → Policies/Password: حدّ أدنى 10 أحرف (وحماية كلمات المرور المسرّبة إن كانت متاحة في خطتك).
- [ ] Authentication → Sessions: مدة JWT (افتراضي ساعة) مقبولة؛ لا تُطيلها.
- [ ] **فعّل المصادقة الثنائية (2FA) على حسابات Supabase وVercel وGitHub** — اختراق أي منها يعني اختراق كل العملاء.
- [ ] Project Settings → Data API: تأكد أن `public` فقط معرَّض.
- [ ] Database → Backups: فعّل (Pro) وجرّب **الاستعادة** مرة كل ربع سنة على مشروع تجريبي.
- [ ] Vercel: لوحة المطور كمشروع ثالث **محمي** (Deployment Protection / كلمة مرور)، ورابطها غير معلن، و`DEVELOPER_SECRET` ≥ 24 حرفًا.
- [ ] لا تضبط `PLUGIN_PUBLIC_KEY` على نشر العملاء إلا إن احتجت مثبّت الإضافات (يسمح بتثبيت كود موقَّع على الخادم)؛ مفتاح التوقيع الخاص يبقى مطفأً عن الإنترنت.

## 5) قرار العزل بين العملاء
- **مشروع Supabase واحد لكل عملائك (الافتراضي هنا):** أرخص وأسهل؛ العزل بـ RLS (مُختبَر آليًا). أي خلل مستقبلي في سياسة يؤثر على الجميع، فأبقِ اختبارات CI إلزامية قبل أي دمج.
- **مشروع لكل عميل:** عزل أقوى وإمكانية تسليم/حذف بيانات عميل بسهولة، وتكلفة أعلى. أنصح به للعملاء الكبار أو الحساسين.
- الهوية البصرية (`brand.json`) لكل **نشر**: عملاء بشعارات مختلفة = مشروع Vercel للواجهة لكل عميل (قاعدة واحدة أو أكثر).

## 6) تشغيل ومراقبة
- اختبار الدخان بعد كل نشر: `tools/smoke-test.mjs` (يفحص الإغلاق والترويسات والتسجيل والـ bootstrap).
- راقب: Supabase Logs (Auth/DB)، Vercel Logs، حجم القاعدة، وتنبيهات فشل `db-backup.yml`.
- سجّل في عقدك مع العميل: ملكية البيانات، التصدير عند الإنهاء، مسؤولية النسخ الاحتياطي، وحق الإيقاف عند عدم السداد. **اطلب مراجعة قانونية** (خصوصية/حماية بيانات حسب بلد العميل).

## 7) ما لا أستطيع ضمانه
لا يوجد نظام «بلا ثغرات». هذه الحزمة تغلق ما وجدته وما أستطيع اختباره آليًا، لكن قبل تسليمه لعميل حقيقي: شغّل CI كاملًا، اجتز اختبار الدخان، ويُفضَّل اختبار اختراق مستقل (حتى لو يوم واحد) على نسخة Staging، خصوصًا منطق الصلاحيات في Express.
