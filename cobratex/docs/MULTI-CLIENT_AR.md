# تعدد العملاء: نشر مستقل لكل عميل (استضافة مجانية الآن → مدفوعة لاحقًا)

## النموذج
لكل عميل **نشرٌ مستقل**: مشروع Supabase خاص به (قاعدة بيانات + مصادقة + تخزين) + مشروعا Vercel (واجهة `slug` وباك إند `slug-api`).
العزل هنا **فيزيائي** (قاعدة مستقلة) وهو أقوى من العزل بـ RLS وحده. كود واحد في مستودع واحد (خاص عندك)، ويُنشر لكل العملاء بضغطة (`Release to clients`).

```
مستودعك الخاص ──► GitHub Actions ──► Vercel (حساب العميل A) + Supabase (مشروع A)
                                  ├─► Vercel (حساب العميل B) + Supabase (مشروع B)
                                  └─► …
لوحة المطور (مشروع Vercel ثالث محمي) ──► تتنقل بين كل الخوادم وتتحكم بكل عميل
```

## ⚠️ قبل أن تبدأ (حقائق مهمة)
1. **املك أنت الحسابات.** أنشئ كل حساب بإيميل تملكه (مثل `acme.cobratex@نطاقك`) ولا تسلّم العميل أي مفتاح. من يملك حساب Vercel/Supabase يملك الوصول للبيانات والنشر. أعطِ العميل **الرابط أو ملف exe فقط**.
2. **الربط مع GitHub:** حساب GitHub واحد لا يُربط إلا بحساب Vercel واحد، لذلك لا نعتمد الربط التلقائي؛ ننشر بـ **Vercel CLI + توكن كل حساب** (workflow `Release to clients`). هكذا لا يطّلع أي عميل على المستودع.
3. **حدود الخطط المجانية (راجع الشروط الحالية عند كل مزوّد):**
   - Supabase المجانية: تتوقف بعد أسبوع بلا نشاط، **بلا نسخ احتياطية يومية**، وعدد المشاريع المجانية محدود لكل منظمة. (سكربت النسخ الليلي أدناه يحل النسخ ويُبقي المشروع نشطًا.)
   - Vercel Hobby مخصصة حسب شروطها للاستخدام غير التجاري؛ نظام يُباع لعميل تجاري يلزمه عادةً Pro.
   - إنشاء حسابات مجانية متعددة لتجاوز حدود خطة قد يخالف شروط المزوّد؛ تأكد قبل التوسع، وخطط للانتقال للمدفوع مبكرًا.
4. **مسار الترقية:** عند أول عميل يدفع، رقِّ مشروع Supabase الخاص به إلى Pro (نسخ احتياطية + بلا إيقاف) ونقل مشروعي Vercel إلى فريق Pro واحد عندك (فريق واحد يحتمل مشاريع عملاء كثيرة). لا يتغير الكود ولا بيانات العميل.

## إضافة عميل جديد (≈ 20 دقيقة)
1. **حسابان بإيميل خاص بالعميل (تملكه أنت):** Supabase (مشروع جديد، اختر منطقة قريبة) و Vercel.
2. من Supabase ← Connect: انسخ **Session pooler** (للأوامر). ثم من جهازك:
   ```bash
   cd backend && npm install && cd ..
   bash tools/new-client.sh acme "postgresql://postgres.xxxx:كلمة-المرور@aws-0-....pooler.supabase.com:5432/postgres" --with-tests
   ```
   يطبّق مخطط القاعدة + ملفات Supabase، ويشغّل اختبارات الأمان (تُلغى تلقائيًا)، ويكتب `clients/acme.env` بأسرار **عشوائية فريدة** لهذا العميل (JWT، BOOTSTRAP، DEVELOPER، رمز 2FA، CRON). المجلد `clients/` خارج git ولا يُرفع أبدًا.
3. **Supabase:** Authentication ← Hooks ← فعّل `public.custom_access_token_hook` · وعطّل «Allow new users to sign up».
4. **Vercel (حساب العميل):** أنشئ مشروعين من أي مستودع (أو استوردهما بالـ CLI):
   `acme` (Root Directory = `frontend`) و`acme-api` (Root Directory = `backend`) والصق متغيرات `clients/acme.env` في كلٍّ منهما. اضبط `SUPABASE_URL` و`VITE_*` الحقيقية.
5. أنشئ **توكن Vercel** (Account Settings ← Tokens) وسجّل `org_id` ومعرّفَي المشروعين (Settings ← General) وأضفها لسر GitHub **`CLIENTS_JSON`**:
   ```json
   { "acme": { "vercel_token": "…", "org_id": "…", "frontend_project_id": "prj_…", "backend_project_id": "prj_…" } }
   ```
   وأضف رابط القاعدة لسر **`CLIENT_DB_URLS`**: `{ "acme": "postgresql://…:5432/postgres" }` (للنسخ الليلي وإبقاء المشروع نشطًا).
6. **أول نشر:** GitHub ← Actions ← **Release to clients** ← `slugs = acme`.
7. **أنشئ شركة العميل ومالكها** (مرة واحدة) عبر `/api/bootstrap` بترويسة `x-bootstrap-secret` من `clients/acme.env`.
8. **لوحة المطور:** 🖧 الخوادم ← أضف `https://acme-api.vercel.app` ← ادخل (كلمة المرور + رمز التحقق) ← **التراخيص** للعميل (الباقة وتاريخ الانتهاء وفترة السماح).
9. اختبار الدخان على النشر: `tools/smoke-test.mjs` (راجع `docs/GO-LIVE_AR.md` §6).
10. سلّم العميل **الرابط** (أو ملف exe: Actions ← *Build Windows installer* ← رابط العميل). مالك الشركة ينشئ بقية مستخدميه بنفسه (انظر `docs/OPERATIONS_AR.md`).

## تحديث كل العملاء عن بُعد
1. عدّل الكود → ارفع رقم `version` في `frontend/package.json` → `git push` (يجب أن ينجح CI).
2. **Actions ← Release to clients** ← `all` (أو أسماء محددة) ← `both`. تُنشر النسخة لكل العملاء بالتوازي (3 في آن واحد) ويستمر الباقون إن فشل أحدهم.
3. من لوحة المطور ← «التحديثات عن بُعد»: أظهر لافتة «إصدار جديد» للجميع، أو **أجبرهم** (أدنى إصدار) قبل العمل. تعمل لكل عميل على حدة.
4. تغييرات قاعدة البيانات (ملف SQL جديد): شغّله على قاعدة كل عميل (`psql` أو `tools/new-client.sh`‐style loop) **قبل** نشر الكود الذي يعتمد عليه. اجعل الملفات دائمًا idempotent (`create or replace`, `if not exists`).

## النسخ الاحتياطي والاستمرارية
- `db-backup.yml` يعمل ليلًا لكل عميل في `CLIENT_DB_URLS`: نسخة **مشفّرة** (GPG) تُحفظ 14 يومًا، وفشل أحدهم لا يوقف البقية. وهو أيضًا نشاط يومي يمنع إيقاف مشاريع Supabase المجانية.
- احتفظ بكلمة `BACKUP_PASSPHRASE` في مدير كلمات مرور. **جرّب الاستعادة** على مشروع تجريبي مرة كل ربع سنة.
- نسخ GitHub Artifacts للبيانات المحاسبية مشروط بأن المستودع **خاص**.

## تجميع العملاء لاحقًا في قاعدة واحدة (اختياري)
التطبيق يدعم المستأجرين (tenants) أصلًا، لكن دمج قواعد منفصلة لاحقًا عمل هجرة حقيقي. الأسهل عمليًا: ابقَ على قاعدة لكل عميل (Pro لكل عميل يدفع).
